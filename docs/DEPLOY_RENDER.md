# Deploy to Render

Render runs a normal, always-on Node process, which is the only thing GroupLore
needs for live games: one process holding the Server-Sent Events stream and the
in-memory game engine. `render.yaml` at the repo root describes that service, so
there is nothing to configure by hand beyond the secrets.

Do not deploy to Vercel or another function platform: see
[DEPLOYMENT.md](./DEPLOYMENT.md#do-not-deploy-to-vercel-or-another-serverless-platform)
for why that produces the "Connection lost — reconnecting" loop.

## What the blueprint sets up

| Setting | Value | Why |
| --- | --- | --- |
| Runtime | Node 22.11.0 | Next.js 16 needs Node 20.9+; this repo targets 22 |
| Build | `npm ci && npm run build` | Reproducible install from the lockfile |
| Start | `npm start` | `next start`, serving pages, REST and SSE together |
| Instances | `1` | Rooms, timers and streams are process-local |
| Plan | `free` | No cost. Sleeps after 15 idle minutes, so pair it with the keep-awake ping below; `0.5c-512mb` (paid, ~$7/mo) never sleeps |
| Health check | `/api/health` | Render restarts the service if it fails |
| Region | `singapore` | Change it if your group is elsewhere |
| Preview environments | off | A preview would be a second copy with its own rooms |
| Auto deploy | every commit to `main` | Each deploy restarts the process, which drops live rooms |

## One-time setup

1. Push `main` to the GitHub repo Render will read. The deployment builds from
   git, not from your machine.
2. In the Render Dashboard: **New → Blueprint**, pick the repository, and use
   the `main` branch. Render finds `render.yaml` and shows the service it will
   create.
3. Fill in each value marked `sync: false` when prompted. They are listed below.
4. **Create** the service. The first build installs, builds, and starts the
   server; the deploy is only live once `/api/health` answers `200`.
5. Copy the service URL (`https://<name>.onrender.com`) and do the Supabase
   steps further down before inviting anyone.

## Environment-variable checklist

Render asks for the `sync: false` rows during Blueprint creation; the rest are
written by `render.yaml`. Add or change values later under
**Service → Environment** (changing a `NEXT_PUBLIC_*` value needs a redeploy,
because those are baked into the browser bundle at build time).

| Variable | Value | Required | Notes |
| --- | --- | --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | Supabase → Project Settings → API → Project URL | yes | Browser-visible; baked in at build |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Supabase → API → `anon` public key | yes | Browser-visible; baked in at build |
| `SUPABASE_URL` | Same project URL | yes | Server only |
| `SUPABASE_SERVICE_ROLE_KEY` | Supabase → API → `service_role` key | yes | Server only. Never rename it to `NEXT_PUBLIC_*` |
| `SESSION_SECRET` | Generated by Render (`generateValue: true`) | yes | HMAC key for reconnect seat tokens; must be long and stable across restarts |
| `UPLOADTHING_TOKEN` | UploadThing dashboard | only for image uploads | Lore profile images fail without it; the game itself does not |
| `ALLOW_GUESTS` | `true` or `false` | yes | Must match Supabase: if anonymous sign-ins are disabled there, set `false` here too |
| `LORE_MODE` | `false` | yes | Enables lore profile prompts |
| `MAX_CONTENT_RATING` | `family`, `teen` or `mature` | yes | Deployment-wide content ceiling |
| `ALLOW_NSFW_CONTENT` | `false` | yes | Hides NSFW-rated prompt banks unless `true` |
| `NODE_VERSION` | `22.11.0` | set by blueprint | Any Node 22.x works |
| `NODE_ENV` | `production` | set by blueprint | |
| `PORT` | **do not set** | — | Render injects it and `next start` reads it; a hardcoded `3000` breaks the port mapping |
| `VERCEL` / `GROUPLORE_ALLOW_SERVERLESS` | **do not set** | — | These switch on the serverless guard, which would return `503 realtime_requires_persistent_host` |
| `DISCONNECT_GRACE_MS`, `RESTORE_TIMEOUT_MS` | unset | no | Optional engine tuning; defaults are fine |

## Supabase settings that must match

- **Auth → URL Configuration**: set *Site URL* to `https://<name>.onrender.com`
  and add `https://<name>.onrender.com/**` to *Redirect URLs*. Without this,
  email confirmation and password reset links bounce to the old Vercel host.
- **Auth → Providers → Anonymous sign-ins**: enable it if `ALLOW_GUESTS=true`.
  If it stays disabled, set `ALLOW_GUESTS=false`; otherwise guests see sign-in
  errors and `/api/health` still reports `guests: true`.
- **SQL migrations**: the schema and migrations in `supabase/` must already be
  applied to that project. The deploy does not run them.

## Keeping it to one instance

- Leave `numInstances: 1`. Render autoscaling is a Pro feature; turning it on
  would put players on different processes and bring back
  `409 connection_not_found`.
- Do not re-enable preview environments (`previews.generation` stays `off`).
- Every deploy restarts the process and drops in-memory rooms. Deploy when
  nobody is playing, or set **Auto-Deploy** to *Off* in the dashboard and ship
  deliberately.
- The `free` plan spins the service down after 15 minutes without inbound
  traffic. Keep it warm with the ping in the next section, or upgrade the
  service's compute plan to `0.5c-512mb` to remove the sleeping entirely.

## Free plan: keeping the service awake

`render.yaml` asks for `plan: free`. Nothing in the app breaks on free; the only
problem is that Render spins a free web service down after 15 minutes without
inbound traffic, and waking it takes about a minute. A friend opening a shared
link in that state sees Render's loading page, not the game. An outside request
every few minutes keeps it from ever getting there.

- **Free instance hours:** 750 per workspace per calendar month. A 31-day month
  is 744 hours, so one service kept awake around the clock uses essentially the
  whole allowance. Don't add a second always-awake free service, and if the
  hours run out Render suspends every free service in the workspace until the
  1st of the next month.
- **Size:** 0.1 CPU and 512 MB. Fine for a few friends; not for a big room.
- **Restarts:** Render may restart a free instance at any time, and every
  restart drops the in-memory rooms. Players reopen the game and rejoin with the
  same lobby code; nothing is lost from the database.

### The keep-alive ping (cron-job.org)

Nothing here runs on GitHub and nothing is added to this repo — GitHub is only
where Render reads the source from. cron-job.org is a website that sends one HTTP
request on a schedule, from its own servers, to whatever URL you give it.

1. Sign up at [cron-job.org](https://cron-job.org) and choose **Create cronjob**.
2. Title `GroupLore keep-alive`; URL `https://<name>.onrender.com/api/health`.
3. Method **GET**. Schedule **every 10 minutes** — anything under 15 works.
4. Leave the timeout at the default 30 seconds. Enable failure email
   notifications if you want to hear about an outage.
5. Save, then use **Test run**: expect `200` and
   `{"status":"ok","timestamp":"...","engine":{"rooms":0},"guests":true}`.

Expect the first ping after a sleep to report a timeout at 30 seconds, because
the service takes about a minute to wake — the wake still happened. Repeated
failures mean the service is not starting at all: read **Logs** in Render.

Point the job at `/api/health`, not `/api/realtime/stream`: the stream requires
a signed-in session and holds the connection open until the timeout.

## Verify live play after the deploy

Do these against the Render URL, not localhost:

```bash
curl --fail https://<name>.onrender.com/api/health
# {"status":"ok","timestamp":"...","engine":{"rooms":0},"guests":true}

curl -i https://<name>.onrender.com/api/realtime/stream
# 401 unauthorized without a token. A 503 realtime_requires_persistent_host
# means VERCEL or GROUPLORE_ALLOW_SERVERLESS is set on the service.
```

Then, in two browsers:

1. Sign in (or join as a guest), open the same lobby code, and confirm both
   screens update live when one changes a setting.
2. Start a game and play a full round: every player's screen must keep
   updating through the whole round, with no "Connection lost" banner.
3. In DevTools → Network, `/api/realtime/stream` must stay one open
   `text/event-stream` request with a `ping` comment roughly every 15 seconds —
   not a request that repeatedly ends and reconnects.
4. If a player reloads mid-game, they should reclaim their seat instead of
   being treated as a new player.

## Moving the public link

The old `mygrouplore.vercel.app` deployment still serves the broken version. If
it stays online, shared links can land there and the reconnect bug reappears.
Point the link you give friends at the Render URL, or unpublish the Vercel
project once the Render service is verified.

## Rollback

Render keeps previous deploys: **Service → Deploys → ⋯ → Rollback** restarts the
previous build. Room state is lost either way, so players rejoin from their
lobby. If you changed `NEXT_PUBLIC_*` values before the deploy, the rollback
returns the old values too, because they are build-time constants.
